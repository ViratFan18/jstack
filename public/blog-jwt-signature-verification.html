TOKENS · PRACTICAL GUIDE

JWT decoding is not signature verification

A compact token can be readable and still be forged, expired, intended for a different service, or not authorized for an operation. Treat inspection and trust as separate steps.

1. A signed JWT is not encrypted

A compact JSON Web Signature (JWS) commonly contains three Base64URL-encoded parts: a JOSE header, claims payload, and signature. Base64URL is an encoding, not secrecy. Anyone holding the token can usually inspect its first two parts.

For a harmless local inspection, Java can decode the header and payload without asserting that the token is genuine:

import java.nio.charset.StandardCharsets;
import java.util.Base64;

String[] parts = compactToken.split("\\.", -1);
if (parts.length != 3) {
    throw new IllegalArgumentException("Expected a compact JWS");
}
String header = new String(
    Base64.getUrlDecoder().decode(parts[0]), StandardCharsets.UTF_8);
String claims = new String(
    Base64.getUrlDecoder().decode(parts[1]), StandardCharsets.UTF_8);

This code does not verify the signature, expiry, issuer, audience, or permissions. Do not make an access-control decision from decoded claims.

2. Validate with application-owned expectations

A robust resource server chooses trusted keys and an allowed algorithm independently of untrusted token input. It then verifies the signature and checks required claims in the context of the service. In Spring Security, begin with the resource-server integration rather than writing a bearer-token parser:

http
    .authorizeHttpRequests(authorize -> authorize
        .requestMatchers("/health").permitAll()
        .anyRequest().authenticated())
    .oauth2ResourceServer(resourceServer ->
        resourceServer.jwt(Customizer.withDefaults()));

Configure the trusted issuer for the environment, and add audience validation when the service requires a particular audience. Confirm expiry and not-before handling, key rotation behavior, and the algorithm policy against the exact Spring Security version and identity provider in use. A valid signature alone does not grant access.

  1. Reject malformed tokens and unexpected compact serialization.
  2. Use trusted issuer metadata or a securely provisioned key; do not fetch arbitrary key URLs from a token.
  3. Allow only algorithms and key types configured for the application.
  4. Validate the expected issuer, audience, expiry, and any required application claims.
  5. Apply endpoint authorization after authentication succeeds.

3. Use a decoder only for inspection

The JStack JWT decoder labels its output as decoded and unverified. It runs locally in the browser, but that does not make the decoded values trustworthy. The separate JWT signature verifier can check a signature with a supplied key; its result still does not replace issuer, audience, authorization, or deployment-specific validation.

Use synthetic examples in tools and screenshots. Do not share production tokens, signing keys, or decrypted claims in logs, issue reports, analytics, or URLs. A bearer token can grant access to whoever obtains it.

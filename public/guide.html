JWT and Java backend security: practical guide

Use the right operation for the job. Encoding changes representation; signing provides integrity; encryption protects content confidentiality.

Decoding a JWT is not verification

A compact signed JWT (JWS) has three dot-separated parts: a JOSE header, a claims payload, and a signature. The first two parts are Base64URL-encoded JSON. Anyone who has the token can usually decode and read those parts. A decoded payload is not proof that the token came from a trusted issuer or has not been changed.

To verify a JWS, validate its signature using the expected algorithm and the correct key. Also check the claims your application relies on, such as issuer (`iss`), audience (`aud`), expiration (`exp`), and not-before (`nbf`). A valid signature alone does not grant authorization; your application must still decide whether the subject may perform the requested action.

Inspect JWT parts in Java without trusting them

The JDK URL-safe Base64 decoder can display the header and payload. This example deliberately does not verify a signature or validate claims; never use its decoded values as authenticated identity.

import java.nio.charset.StandardCharsets;
import java.util.Base64;

public final class InspectJwt {
    public static void main(String[] args) {
        String token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJqYXZhLWRldiIsInJvbGUiOiJlbmdpbmVlciIsImlhdCI6MTcwNDA2NzIwMH0.c2FtcGxlLXNpZ25hdHVyZQ";
        String[] parts = token.split("\\.", -1);
        if (parts.length != 3) {
            throw new IllegalArgumentException("Expected a compact JWS with three parts");
        }

        String header = new String(Base64.getUrlDecoder().decode(parts[0]), StandardCharsets.UTF_8);
        String claims = new String(Base64.getUrlDecoder().decode(parts[1]), StandardCharsets.UTF_8);
        System.out.println(header);
        System.out.println(claims);
    }
}

Save as InspectJwt.java, then run javac InspectJwt.java && java InspectJwt. The JDK decoder accepts unpadded Base64URL. Decoding only reveals bytes; use a maintained JOSE library for verification.

Symmetric and asymmetric signatures

HMAC algorithms such as HS256 use one shared secret to sign and verify. Every verifier holding that secret can also create signatures, so sharing it expands who can issue tokens. RSA and ECDSA signature schemes use a private key to sign and a public key to verify. Keep private keys secret, and distribute public keys only through channels your system trusts.

Choose an algorithm from application configuration rather than trusting an unverified token header to choose arbitrary verification behavior. The JStack workbench restricts each verification call to the algorithm selected in its control.

Algorithm and key guidance

Allowlist the algorithms your service expects and reject unexpected algorithms instead of letting an untrusted header select policy. RFC 7518 requires an HMAC key at least as large as the hash output (256 bits for HS256) and RSA keys of 2048 bits or larger for the specified RSA signature algorithms. ES256 uses the P-256 curve. Keep keys out of source control, logs, URLs, and client-side code; use your platform's secret or key-management service and plan rotation.

For Spring Security, configure a trusted issuer and use the resource-server support rather than hand-parsing tokens. This Spring Security 6 example expects the corresponding OAuth2 resource-server dependencies and issuer configuration:

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
class ApiSecurity {
    @Bean
    SecurityFilterChain apiSecurity(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(authorize -> authorize
                .requestMatchers("/health").permitAll()
                .anyRequest().authenticated())
            .oauth2ResourceServer(resourceServer ->
                resourceServer.jwt(Customizer.withDefaults()))
            .build();
    }
}
spring.security.oauth2.resourceserver.jwt.issuer-uri=https://issuer.example

Configure audience validation and application authorization for your own API as well; issuer-based JWT decoding alone is not an access-control policy. See the Spring Security JWT resource-server reference.

Common JWT integration errors

A malformed compact token usually has the wrong number of dot-separated parts or invalid Base64URL data. A signature failure often means the wrong key, algorithm, or key encoding was selected. Expiration failures can come from an expired exp claim or a system clock that is out of sync; JWT NumericDate values are seconds, not Java milliseconds. Issuer and audience failures mean the token does not match the resource server's configured trust context. Diagnose these conditions without logging bearer tokens or keys.

Signing is different from encryption

A JWS signature detects changes and authenticates a token relative to a trusted key, but it does not hide the header or payload. A JWE is an encrypted token with five compact parts and uses key management plus a content-encryption algorithm. Anyone who needs to read a JWE must have the appropriate decryption key.

Encryption does not replace authorization or key management. Use a maintained library, validate supported algorithm/key combinations, protect keys, and avoid sending secrets in URLs or logs.

JSON validation checks syntax, not meaning

Valid JSON follows the JSON grammar: strings use double quotes, object names are quoted, and trailing commas are not permitted. A syntax validator can tell you whether parsing succeeds. It cannot decide whether a field is required, whether a number is in range, or whether the document matches your API contract; use a schema or application-specific validation for those checks.

Base64 is not encryption

Standard Base64 represents bytes with printable characters and padding. It offers no confidentiality and no integrity protection. Use it for transport or text representation only; do not treat an encoded password, token, or key as protected. Base64URL is a related variant with different characters and padding conventions, commonly used inside JWTs.

JStack Base128 is a custom format

The JStack Base128 converter packs UTF-8 bytes into seven-bit groups and maps each group to a Braille symbol from U+2801–U+2880. This is not a universal Base128 standard; use the matching JStack decoder for round-trips.

Generate Java models from JSON

The JSON-to-Java generator creates nested records or POJOs from a sample object. Treat the result as a starting model, not an API schema: mixed, empty, or null-only values may become Object, and renamed properties use Jackson annotations.

Use local tools carefully

JStack performs supported operations in the current browser and does not send tool inputs to a JStack application backend. However, the deployed page and its hosting provider remain part of your trust boundary. For production credentials, use a tool whose code and hosting you have reviewed, and independently verify critical results.

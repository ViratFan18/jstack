From a JSON example to a Java model

A generator can save repetitive typing, but a sample response is evidence about one example, not a complete API contract. Use inference as a draft and validate the model against the real requirements.

Start with representative data

Consider a response that has nested data and a collection:

{
  "id": 42,
  "displayName": "Ada Lovelace",
  "active": true,
  "roles": ["admin", "author"],
  "address": {
    "city": "London",
    "postalCode": "N1"
  }
}

After checking its syntax with a JSON validator, a plausible Java 16+ record model is:

import java.util.List;

public record User(
    Long id,
    String displayName,
    Boolean active,
    List<String> roles,
    Address address
) {
    public record Address(String city, String postalCode) {}
}

Compile generated output in the target Java version. Add the package, imports, serialization configuration, validation, and constructors that your application actually needs.

Inference has limits

  • Optional fields: a single fixture cannot show whether a field may be omitted in another response.
  • Null values: a null-only value does not reveal the intended Java type. A generator may use Object until you provide a better example.
  • Arrays: one array sample may not include every variant. Mixed values need an explicit domain model or a deliberate broad type.
  • Numbers: a sample cannot express the allowed range, precision, or whether a value is an identifier rather than a quantity.
  • Names: Java identifiers may need normalization. If the generated field name differs from the JSON key, review the serialization annotation and required dependency.

For stable APIs, treat an OpenAPI document, JSON Schema, or an explicitly maintained contract as the source of truth. A generated model is not schema validation and does not guarantee future compatibility.

A review checklist

  1. Use fixtures for typical, minimal, nullable, and alternate response variants.
  2. Check primitive versus wrapper types and the project's nullability conventions.
  3. Verify nested collection types and key-to-field mappings.
  4. Compile with the target Java release and serialization library.
  5. Add tests that deserialize representative fixtures and reject invalid cases.

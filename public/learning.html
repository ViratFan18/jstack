1. Inspect a JWT, then verify it with application policy

A compact signed JWT (JWS) has three dot-separated parts. The header and claims are Base64URL-encoded, not encrypted. Decoding can help diagnose a token, but the result is untrusted until a server verifies it with an expected algorithm and key.

For a quick, non-authenticating inspection in Java, the JDK URL-safe decoder can display the first two parts. This synthetic token has a placeholder signature and is included only to demonstrate decoding:

import java.nio.charset.StandardCharsets;
import java.util.Base64;

public final class JwtPartsInspection {
    public static void main(String[] args) {
        String token = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJkZW1vIn0.cGxhY2Vob2xkZXI";
        String[] parts = token.split("\\.", -1);
        if (parts.length != 3) {
            throw new IllegalArgumentException("Expected a compact JWS");
        }

        String header = new String(
            Base64.getUrlDecoder().decode(parts[0]), StandardCharsets.UTF_8);
        String claims = new String(
            Base64.getUrlDecoder().decode(parts[1]), StandardCharsets.UTF_8);
        System.out.println(header);
        System.out.println(claims);
    }
}

Save as JwtPartsInspection.java, then run javac JwtPartsInspection.java && java JwtPartsInspection. This code only decodes; it does not verify a signature or claims. In a Spring resource server, configure a trusted issuer and allowlisted algorithms through the framework rather than hand-parsing a bearer token:

http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/health").permitAll()
        .anyRequest().authenticated())
    .oauth2ResourceServer(resource -> resource.jwt());

Then configure the issuer for your environment and add audience validation and application authorization when required. A verified signature is not an access-control decision. Use the decoder only for inspection and the verifier for a separate, local check with the expected key. For a longer validation checklist, see JWT decoding versus signature verification.

2. Turn a JSON example into a Java model you can review

Start from a representative response rather than an empty or partial object. For example:

{
  "id": 42,
  "displayName": "Ada Lovelace",
  "active": true,
  "roles": ["admin", "author"],
  "address": { "city": "London", "postalCode": "N1" }
}

After checking its syntax, generate a record or POJO. Review every inferred type against the actual API contract: one sample cannot reveal optional fields, future enum values, numeric ranges, or all variants in a collection. A null-only or empty sample may reasonably infer Object; a renamed Java field may require Jackson's @JsonProperty.

For a record, a representative shape might be:

import java.util.List;

public record User(
    Long id,
    String displayName,
    Boolean active,
    List<String> roles,
    Address address
) {
    public record Address(String city, String postalCode) {}
}

This is illustrative, not the output contract for every input: JStack's generator may use wrappers or annotations based on the sample and selected style. Add imports, package declarations, validation, serialization configuration, and tests for your project. Try the JSON syntax checker and model generator.

3. Decide between JWS and JWE before choosing a tool

JWS signs content to detect unauthorized changes when verified with the right key. The payload is still readable. JWE encrypts content for confidentiality and requires the matching decryption key. Encryption does not decide whether a caller is authorized, and key distribution remains your responsibility.

  • Use JWS signing when the consumer needs to verify integrity and issuer trust.
  • Use JWE encryption only when the recipient needs confidentiality and the selected key arrangement is appropriate.
  • Keep private keys and shared secrets out of source control, logs, URLs, and support messages.

In the workbench, direct dir/A256GCM uses a 32-byte shared key. RSA-OAEP-256 uses a public key to encrypt and its matching private key to decrypt. Treat every generated key and decrypted result as sensitive.

4. Know what text encodings do

Base64 represents bytes using printable characters; it provides no secrecy or integrity. Standard Base64 and Base64URL have different alphabets, and the text converter accepts standard Base64—not arbitrary binary files or JWT-specific Base64URL parts.

JStack Base128 is a custom mapping that packs UTF-8 bytes into seven-bit groups and maps them to Braille symbols U+2801–U+2880. It is not a universal standard. Use the matching JStack decoder for round-trips. Explore Base64 or JStack Base128 with harmless sample text.

5. A small debugging checklist

  1. Keep the original input and record the exact, non-secret error.
  2. For JSON, check double-quoted keys and strings, commas, and trailing commas; syntax validity is not schema validity.
  3. For a JWS, confirm the compact token has three parts; a compact JWE has five.
  4. For verification, check the configured algorithm, matching key format, issuer, audience, and NumericDate units (seconds).
  5. For generated Java, compile it in the target Java version and add project-specific imports and tests.

Do not include bearer tokens, private keys, passwords, or other secrets in bug reports. The developer guide covers these boundaries in more detail.
